# Деплой на сервер

## Почему docker-compose.prod.yml отдельный

На хакатонном сервере уже крутятся чужие контейнеры. Чтобы не сломать их, сделал отдельный prod-файл:
- порт PostgreSQL не торчит наружу (нет конфликта с чужим postgres на 5432)
- контейнеры с уникальными именами: `sferumburo_bot_prod`, `sferumburo_postgres_prod`
- база хранится в отдельном volume `sferumburo_pgdata_prod`

## Шаг 1 — загрузить файлы

Через FileZilla или git clone закинуть на сервер:
- `sferum_buro_bot.py`
- `requirements.txt`
- `Dockerfile`
- `docker-compose.prod.yml`
- `.env` (может быть скрытым — включи показ скрытых файлов в FileZilla)
- папку `webapp/`

## Шаг 2 — запуск

```bash
cd /путь/до/папки
docker compose -f docker-compose.prod.yml up -d --build
```

## Шаг 3 — проверка

```bash
docker ps
```

Должны быть видны `sferumburo_bot_prod` и `sferumburo_postgres_prod` со статусом `Up`.

Если что-то не так — смотреть логи:
```bash
docker logs -f sferumburo_bot_prod
```

## Про фотографии

Фото не скачиваются на сервер — бот сохраняет только file_id из МАКСа и отдаёт его обратно при показе. Место на диске не тратится.

## Об использовании ИИ при разработке

Проект написан самостоятельно, архитектура, логика бота и основной код — результат собственной разработки. В процессе написания и отладки использовался ИИ-ассистент как инструмент: для поиска и исправления багов в продакшене, ревью безопасности API-эндпоинтов и помощи с конфигурацией инфраструктуры (nginx, Docker, Postgres). Все решения о том, что и как исправлять, принимались самостоятельно; ИИ не генерировал проект целиком и не заменял разработку.

## Частые проблемы при деплое и их решения

### `.env` пропал или бот падает с `fe_sendauth: no password supplied`
Значит `.env` отсутствует или пуст, а PostgreSQL уже был проинициализирован с другими кредами ранее (volume `sferumburo_pgdata_prod` хранит пароль с первого запуска, переменные окружения при повторных запусках игнорируются). Решение:
1. Проверить, что `.env` реально существует и не пуст: `cat .env`.
2. Если пароль неизвестен — зайти в контейнер Postgres напрямую (локальные подключения разрешены без пароля — `trust` в `pg_hba.conf`) и сменить пароль роли:
   ```bash
   docker exec -it sferumburo_postgres_prod psql -U <имя_роли> -d <имя_базы>
   ALTER USER <имя_роли> WITH PASSWORD 'новый_пароль';
   ```
3. Реальные имя роли и базы, если забыты, можно найти через `strings` по системным файлам кластера:
   ```bash
   docker exec -it sferumburo_postgres_prod sh -c "strings /var/lib/postgresql/data/global/* | sort -u"
   ```
**Профилактика:** держите копию `.env` вне директории проекта (не только на сервере — потеряется вместе с ним).

### Мини-апп не открывается / CSS и JS не подгружаются (404 на `style.css`/`app.js`)
Статика раздаётся по пути `/app/static/...` (см. `add_static` в коде), а не `/app/...` — пути в `index.html` должны начинаться с `static/`, иначе бэкенд вернёт `404` на эти файлы.

### Изменения в CSS/JS не отображаются после пересборки
MAX агрессивно кеширует статику мини-аппа на стороне клиента. При любой правке `style.css`/`app.js` обязательно увеличивайте версию в query-параметре (`?v=N` → `?v=N+1`) в `index.html` — иначе клиент может продолжать показывать старую версию даже после полной пересборки контейнера. Если не помогает — очистить кеш самого приложения MAX на устройстве.

### Доступ к админ-функциям мини-аппа
Эндпоинты `/app/api/admin/*` защищены кодом администратора (тот же код, что активируется в чате командой `/admin <код>`), передаваемым в заголовке `X-Admin-Code`. Без действующего кода, привязанного к пользователю с `is_admin = TRUE`, запросы отклоняются с `403`.

### Если код администратора утерян
На сервере лежит скрипт `reset_admins.sh` (не в репозитории — специфичен для конкретного сервера) для снятия прав со всех админов и выдачи нового кода. Запускать вручную через SSH при необходимости.

## Разная модель доступа к админке в чате и в мини-аппе — это осознанно

В чате с ботом `/admin`-команды проверяются через `db_is_admin(uid)`, где `uid` приходит напрямую от MAX API при получении сообщения — подделать его нельзя, это гарантия платформы. Никакого дополнительного подтверждения там не требуется и не нужно.

В мини-аппе (веб-странице) такой гарантии нет: сервер не может достоверно узнать, кто открыл страницу, потому что MAX не передаёт подписанные данные о пользователе при запуске мини-приложения (в отличие, например, от `initData` в Telegram Mini Apps). Поэтому все `/app/api/admin/*` эндпоинты защищены кодом администратора, передаваемым в заголовке `X-Admin-Code` — тем же кодом, что активируется в чате командой `/admin <код>`. Без него эндпоинты возвращают `403`.

Это выглядит асимметрично, но не является недоработкой: сделать вход в мини-апп таким же бесшовным, как в чате, нельзя технически — убрать проверку кода значит открыть `stats`, `recent`, `list`, `gencode` и `clear` (очистка базы) анонимно, любому, кто откроет страницу.

Если понадобится более удобный UX ввода кода (сейчас это браузерный `prompt()`), это можно заменить на отдельный экран внутри самого мини-аппа в общем стиле — задача чисто косметическая, безопасность не меняется.
